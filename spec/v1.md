## 1. Scope and conformance

**Governs.** The mapping from resolved WIT — the semantics of
`wit-parser::Resolve` upstream — to Java 17 declaration source: types, names,
packages, documentation, generated file shape.

**Does NOT govern.** Canonical ABI lifting/lowering, memory layout, handle
tables, component loading, host/guest glue. Implementations of this spec
produce declarations only; a component runtime adapter consumes them.

**Normative language.** MUST / MUST NOT / SHOULD / MAY per RFC 2119.
A conforming implementation MUST satisfy every MUST; conformance is verified
through the data in [`../conformance/`](../conformance/), which defines two
tiers (§14):

- **Tier 1 (normative).** API-shape equivalence, compared by canonical digest.
  Whitespace and Javadoc prose are not compared.
- **Tier 2 (non-normative).** Byte-level identity. Constrains the reference
  implementation only (its determinism tests), never a second implementation.

## 2. Input model and feature gates

- Input is one WIT world file, or a WIT directory (a package with
  `deps/`), resolved exactly as `wit-parser::Resolve` resolves it: syntax,
  package resolution, dependency resolution, `use`/`include` semantics are
  upstream behavior; this spec does not redefine them.
- **Feature gates.** `@unstable(feature = "x")` items are skipped unless the
  feature is enabled; `@since(version = ...)` items are included from their
  version onward. Implementations MUST expose feature selection equivalent to:
  `--features <name>...` (repeatable) and `--all-features`. Default is
  **no features enabled** (matching upstream `Resolve` defaults). Skipping an
  item due to a disabled feature is not a diagnostic.
- If a package contains several worlds, implementations MUST generate all of
  them by default; `--world <name>` (repeatable) restricts generation to the
  named worlds. World names are kebab labels.
- **All interfaces** in all resolved packages MUST be generated, regardless of
  world membership (worlds additionally generate aggregates, §7). An
  interface no world references is still part of the package's public API.

## 3. Package mapping

### 3.1 WIT package → Java package

```text
ns:pkg@x.y.z  →  [package-root.]<ns>.<pkg>.<version-segment>
```

`ns` and `pkg` are kebab labels; each becomes a Java package segment in
**lowerCamel** form (a single word maps to itself). If the result is a
reserved word (§4.2), mangle it (`class` → `class_`). Every derived segment
mangles the same way — interface (§3.3) and world (§7.1) segments too, so a
world named `default` lands in `default_`. Segment names MUST be
valid Java identifiers and MUST NOT be Java keywords.

### 3.2 Version segment

Given semver `major.minor.patch` with optional pre-release and build metadata:

```text
if major > 0:      seg = "v" + major
else:              seg = "v0_" + minor
if pre-release:    seg = seg + "_" + sanitize(pre-release)
```

- `major == 0` uses the minor because in 0.x the minor is the breaking axis.
- **Build metadata is ignored** (not part of compatibility semantics).
- `sanitize(s)`: lowercase `s`; map every character to `[a-z0-9_]`
  (`a-z0-9` kept; `-`, `.`, `_` → `_`; anything else → `_`); collapse runs of
  `_` to a single `_`; strip leading/trailing `_`; if the result is empty use
  `pre`; if it starts with a digit prefix `_`.

Examples:

| WIT package | Java package |
|---|---|
| `wasi:http@1.2.3` | `wasi.http.v1` |
| `wasi:http@0.2.3` | `wasi.http.v0_2` |
| `wasi:http@0.3.0-draft` | `wasi.http.v0_3_draft` |
| `wasi:foo@0.2.0-rc-2023-11-10` | `wasi.foo.v0_2_rc_2023_11_10` |
| `wasi:foo@0.2.0-alpha.1+b7c` | `wasi.foo.v0_2_alpha_1` |

Two versions of the same package that map to the same Java package but
contain same-named items → WJ0007.

### 3.3 Interface granularity

`--interface-package-style`:

- **`nested`** (default): every WIT interface gets its own sub-package:
  interface `types` of `wasi:http@0.2.0` → `wasi.http.v0_2.types`. The
  interface segment is lowerCamel of the interface name, keyword-mangled as
  above. Same-named types across interfaces can never collide.
- **`flat`**: all interfaces' types land directly in the WIT package's Java
  package. More compact, but same-named types across interfaces → WJ0004.

World-local (inline) type definitions always land in the world's own package
segment (§7), regardless of style.

### 3.4 Explicit overrides

`--package-map <file>` (TOML):

```toml
"wasi:http" = "org.example.wasi.http"
"wasi:io@0.2" = "org.example.wasi.io.v2"
```

Matching precedence: **versioned exact match > unversioned match > default
rule (§3.1–§3.3)**. An override replaces the entire prefix including the
version segment (the value is used verbatim). Override values MUST be valid
Java package names; implementations MUST reject invalid ones up front.

## 4. Names and mangling

### 4.1 Name forms

WIT identifiers are kebab labels (`word ::= [a-z][0-9a-z]*`,
`label ::= word ('-' word)*`). kebab→camel conversion on word boundaries is
**bijective**, so camel forms cannot collide with each other.

| Position | Form | Example |
|---|---|---|
| type, interface, resource, variant case | UpperCamel | `descriptor-flags` → `DescriptorFlags` |
| method, record component, function parameter, accessor | lowerCamel | `last-operand` → `lastOperand` |
| enum constant, flags constant | UPPER_SNAKE | `read-only` → `READ_ONLY` |
| Java package segment | lowerCamel | `incoming-handler` → `incomingHandler` |

### 4.2 Reserved list (frozen)

Extending this list is a breaking change. Two groups, both mangled
**unconditionally** — no signature-compatibility analysis:

1. **Java keywords, reserved literals, and `var`** (JLS §3.9, §3.8, Java 9+):
   `abstract, assert, boolean, break, byte, case, catch, char, class, const,
   continue, default, do, double, else, enum, extends, final, finally, float,
   for, goto, if, implements, import, instanceof, int, interface, long, native,
   new, package, private, protected, public, return, short, static, strictfp,
   super, switch, synchronized, this, throw, throws, transient, try, void,
   volatile, while`, plus the literals `true, false, null`, the reserved name
   `_`, and `var`.
2. **`java.lang.Object` method group** (final methods break interface
   declarations; the rest breaks record accessors or interface overrides):
   `wait, notify, notifyAll, getClass, toString, hashCode, equals, clone,
   finalize`.

Group 2 names are mangled in **lowerCamel positions** — the only positions
where their camel forms can equal an `Object` method name. The UpperCamel and
UPPER_SNAKE forms of the same kebab label (`to-string` → `ToString` /
`TO_STRING`) are distinct legal names and are left untouched.

### 4.3 Mangle algorithm

```text
mangle(name):
    if name ∈ reserved (§4.2):  name = name + "_"
    while name is already assigned in the same scope:  name = name + "_"
    if no free name found after any number of appends:  WJ0005
```

Mangling is deterministic and scope-local. Because WIT identifiers cannot
contain `_` and kebab→camel is bijective, collisions here are rare; the rule
exists so that no implementation ever emits a silent rename.

## 5. Type mappings

Type mappings compose: a type constructor applied to `T` first maps `T`
recursively, then applies its own rule. Every type mentioned below is either a
WIT type definition, a builtin, or a support-package type (§8).

### 5.1 Primitive types

| WIT | Java | Notes |
|---|---|---|
| `bool` | `boolean` | |
| `s8` | `byte` | |
| `s16` | `short` | |
| `s32` | `int` | |
| `s64` | `long` | |
| `u8` | `int` | Java `byte` is signed; MUST NOT be used |
| `u16` | `int` | Java `char` is unsigned-16 but semantically wrong; MUST NOT be used |
| `u32` | `long` | |
| `u64` | `long` | **unsigned semantics lost** — see below |
| `f32` | `float` | |
| `f64` | `double` | |
| `char` | `int` | **MUST NOT map to Java `char`** — see below |
| `string` | `java.lang.String` | never imported; always the simple name |

**`char`.** WIT `char` is a Unicode *scalar value* (U+0000..U+10FFFF, excluding
the surrogate range U+D800..U+DFFF). Java `char` is a UTF-16 code unit and
cannot represent most of that domain; mapping to it would silently corrupt the
supplementary plane. This is a correctness requirement, not style. Every
declaration whose type involves `char` MUST carry this Javadoc (exact wording,
`Long`-style `{@code}` markup):

```text
A Unicode scalar value (U+0000..U+10FFFF, excluding the surrogate range
U+D800..U+DFFF), stored as a Java {@code int}.
```

**`u64`.** The one mapping in v1 that compiles but loses semantics. Every
declaration whose type involves `u64` MUST carry this Javadoc:

```text
Unsigned 64-bit integer, range 0..2^64-1, stored as a Java {@code long},
which is signed. Use {@link java.lang.Long#compareUnsigned},
{@link java.lang.Long#divideUnsigned} and {@link java.lang.Long#toUnsignedString}
for unsigned operations.
```

`--u64=BigInteger` maps `u64` → `java.math.BigInteger` instead (no Javadoc
requirement). Default is `long`.

**`f32`/`f64`.** WIT permits only canonical NaN; Java NaN bit patterns and
comparison semantics differ. Noted once in the support package's
`package-info.java` (§8); not repeated per declaration.

### 5.1.1 Boxing in generic positions

Java generics require reference types. Wherever a primitive-mapped type
appears as a **generic type argument** (`Optional`, `List`, `Result`,
`TupleN`) or under `@Nullable`, it takes its boxed form: `boolean`→`Boolean`,
`byte`→`Byte`, `short`→`Short`, `int`→`Integer`, `long`→`Long`,
`float`→`Float`, `double`→`Double`. `byte[]` is a reference type and stays an
array everywhere. Top-level positions (fields, parameters, returns) keep the
primitive form.

### 5.2 `list<T>`

| WIT | Java |
|---|---|
| `list<u8>`, `list<s8>` | `byte[]` |
| every other `list<T>` | `java.util.List<T>` |

The byte-array special case applies in **all** positions:

| WIT | Java |
|---|---|
| record field `data: list<u8>` | `byte[] data` |
| `option<list<u8>>` (optional style) | `java.util.Optional<byte[]>` |
| `list<list<u8>>` | `java.util.List<byte[]>` |
| `result<list<u8>, E>` | `Result<byte[], E>` |
| parameter / return | same rule |

No other primitive gets an array special case. Rationale: `List<Integer>`
for byte buffers is a performance disaster on real interfaces (WASI is full of
`list<u8>`); `List<Long>` positions are rare enough that rule simplicity wins.

### 5.3 `tuple` and `tuple<>`

| WIT | Java |
|---|---|
| `tuple<A, B>` | support `Tuple2<A, B>` |
| `tuple<A..H>` | support `Tuple3` … `Tuple8` |
| `tuple<>` | support `Unit` |
| arity > 8 | **WJ0002** |

Tuple components are positional and map to fields `v0` … `v7`.
A tuple of two bytes is `Tuple2<Integer, Integer>` (no array special case).

### 5.4 `option<T>`

Two styles, selected by `--option-style`:

- **`optional`** (default): `option<T>` → `java.util.Optional<T>` in **every**
  position — return types, parameters, record components, tuple fields,
  variant payloads, nested inside itself (`option<option<T>>` →
  `Optional<Optional<T>>`). This deliberately violates the Java API-convention
  guidance that `Optional` is return-only, because every alternative collapses
  `some(none)` and `none` (see known-limitations #4).
- **`nullable`**: `option<T>` → bare `T` annotated support `@Nullable`
  (type-use, so it composes: `List<@Nullable String>`) in **non-return
  positions**; return positions remain `Optional<T>`. A nested `option`
  (`option<option<T>>` at any depth) → **WJ0006**, pointing at the nesting
  site. Implementations MUST NOT guess.

### 5.5 `result<T, E>`

Java generics accept no `void`; support `Unit` fills absent sides.

| WIT | Java |
|---|---|
| `result<T, E>` | `Result<T, E>` |
| `result<T>` | `Result<T, Unit>` |
| `result<_, E>` | `Result<Unit, E>` |
| `result` | `Result<Unit, Unit>` |

Errors are **values, not exceptions**: `result` appears in record fields and
list elements where exceptions cannot be expressed, and downstream adapters
translate to control flow themselves. The `Result` source is normative (§8).

### 5.6 `record`

WIT record → Java `record` (Java 17).

- Components in WIT field order; names lowerCamel + §4 mangling.
- The record's Javadoc carries the WIT doc; each component's WIT doc becomes a
  `@param` entry.
- Two components of the same record can never collide (kebab→camel is
  bijective, §4.1), and mangling scope is the single record: a component
  named `class` in one record and a component named `class` in another each
  become `class_` independently.

### 5.7 `enum`

WIT enum → Java `enum`. Constants UPPER_SNAKE (`read-only` → `READ_ONLY`),
in WIT case order. WIT enums have no payloads; none are invented.

### 5.8 `variant`

WIT variant → `sealed interface V permits V.CaseA, V.CaseB, …` with one nested
`record` per case:

```java
public sealed interface Shape permits Shape.Circle, Shape.Nothing {
    record Circle(double value) implements Shape {}
    record Nothing() implements Shape {}
}
```

- Case names UpperCamel; records nested inside the sealed interface (no
  package-namespace pollution); implements list names the outer interface.
- Payload-less case → **empty** record (value semantics come from record
  `equals`/`hashCode`; no `INSTANCE` singletons).
- Payload component is always named `value`; its type maps recursively —
  including resources (e.g. `stream-error.last-operation-failed(error)` maps
  the payload to the resource's Java interface type) and `option` payloads
  (`Optional<T>` per style).
- Records appear in WIT case order; the `permits` list matches.
- Per-case WIT docs land on the nested record.

### 5.9 `flags`

WIT flags → positional record over the raw bits + named constants:

```java
public record DescriptorFlags(long bits) {
    public static final DescriptorFlags READ =
            new DescriptorFlags(1L << 0);
    public static final DescriptorFlags WRITE =
            new DescriptorFlags(1L << 1);
    // one constant per member, value 1L << n in WIT member order

    public DescriptorFlags or(DescriptorFlags other) { … }
    public DescriptorFlags and(DescriptorFlags other) { … }
    public boolean contains(DescriptorFlags other) { … }
    public static DescriptorFlags empty() { … }
}
```

- Method set is **exactly** `or`, `and`, `contains`, `empty()`. No `not`/`xor`
  in v1 (append-only later; downstream can compute on `bits` directly).
- Constants are UPPER_SNAKE `X` instances in WIT member order, bit `1L << n`.
- A flags with **0 members** is legal (`empty()` only); **> 64 members →
  WJ0003**.
- The constructor performs no masking/validation; downstream adapters own
  semantic checks.

### 5.10 Type alias

`type x = y` and `use a.{b as c}` generate **no** Java type. Every reference
resolves to the target type's Java type directly. Java has no aliases; a
wrapping subtype would break value semantics and interchangeability. Alias
intent is not preserved anywhere in the output (known-limitations #5).
Aliases to resources resolve to the same resource interface (§5.11).

### 5.11 `resource` and handles

WIT resource → `public interface X extends AutoCloseable`.

> **Validated by the M2 spike** (see [`../spike/`](../spike/)): a
> Chicory-core lowering implemented these declarations for a
> `wasi:io/streams` subset — including a variant with a resource payload —
> without modifying a single declaration. The handle table lives entirely
> in the adapter.

- `close()` is declared as `void close()` — narrowed from
  `AutoCloseable.close() throws Exception`; it is **idempotent** and
  corresponds to the WIT resource *drop*.
- Instance methods → abstract instance methods on `X`.
- Constructor → nested `public interface Factory { X create(<params>); }`.
  The factory method is always named `create`.
- Static methods → nested `public interface Statics { … }` with lowerCamel
  names. `Factory`/`Statics` separation keeps WIT's separate static/instance
  namespaces collision-free.
- `own<T>` and `borrow<T>` both map to the Java type `T` itself. A bare
  resource type used directly as a type is WIT shorthand for `own<T>` and maps
  identically. The ownership contract is **Javadoc-only**
  (known-limitations #2): a parameter-position `borrow<T>` MUST carry this
  Javadoc on the parameter:

```text
Borrowed handle: ownership is not transferred by this call.
```

  A returned `own<T>` MUST carry:

```text
Owned handle: the caller is responsible for closing (dropping) it.
```

  When an owned handle is **nested** in a composite type (tuple, record,
  list, option, variant payload — e.g. `accept` returning
  `tuple<tcp-socket, input-stream, output-stream>`), the note cannot attach
  per element; the enclosing function's Javadoc MUST instead carry exactly
  one of:

```text
The returned value contains owned handles: the caller is responsible for closing them.
```

```text
A parameter contains owned handles; closing them is the caller's decision.
```

- `equals`/`hashCode` are NOT specified: handle identity is runtime semantics
  and belongs to the adapter (the M2 spike confirmed a handle table lives
  entirely adapter-side; see [`../spike/`](../spike/)).

### 5.12 Unsupported constructs → WJ0001

`future<T>`, `stream<T>`, `error-context`, fixed-size `list<T, N>`,
`map<K, V>`. The diagnostic message MUST name the construct.

- **Async.** `CompletionStage` is a runtime contract without drop semantics;
  `Flow.Publisher` carries the full Reactive Streams obligations
  (backpressure, `request(n)`, cancellation) far beyond declarations. WIT
  futures/streams are ownership-carrying handles. Mapping v2 will revisit
  (leaning toward support-package `WitFuture`/`WitStream`).
- **`map<K, V>`.** Upstream restricts map keys to scalar types and `string`
  (`map<list<u8>, …>` is invalid WIT), so a `java.util.Map<K, V>` mapping
  would be *sound*. It is still rejected in v1: no real-world corpus uses it,
  v1 is append-only (§15), and mapping it now would freeze a contract (null
  handling, mutation, iteration order) before any adapter has pulled on it.
  A v2 may append `map<K, V>` → `java.util.Map<K, V>` for scalar keys.

## 6. Functions and interfaces

- WIT function → abstract method: name lowerCamel (§4.1), parameters in WIT
  order, single result → return type (missing result → `void`). Upstream
  removed multi-value results; none can occur.
- WIT function parameters and results map by §5 rules; `borrow`/`own`
  parameters carry the §5.11 Javadoc notes.
- WIT interface → Java `interface` (UpperCamel), nested style: one interface
  per sub-package with `package-info.java` carrying the WIT interface doc;
  flat style: one interface among others in the WIT package's Java package.
- Function-level WIT docs → method Javadoc; parameter docs → `@param`.
- Every WIT interface emits its Java interface declaration file, even when
  it declares no functions of its own: world accessors return the interface
  type, so the named type must exist. Generated packages therefore never
  have "phantom" types that exist only as accessor targets.
- **Interface declaration vs member name.** WIT keeps interface names and
  member names in separate scopes, so an interface may repeat its own name on
  a member (`interface error { resource error; }` — used by real WASI for
  `error`, `network`, `terminal-input`, `terminal-output`). Java cannot: both
  land as `UpperCamel` types in the same package (nested style). The
  **interface declaration** mangles via §4.3 (`Error_`); member types keep
  their WIT-derived names, because they dominate real signatures. World
  accessors return the mangled declaration type. This is the only situation
  in which a generated declaration name carries a mangle suffix without a
  reserved-word hit.
- `static` functions (free functions in WIT are already static-like) are
  abstract methods on the interface; there is no `Statics` split outside
  resources.

## 7. Worlds and role

Direction semantics: in a WIT world, `import` means *provided to the guest*;
`export` means *implemented by the guest*. For a host-side embedder these
flip: host **implements** the imports, host **calls** the exports. The spec
encodes the host's point of view in Javadoc; type shapes are identical.

### 7.1 Aggregate layout

```text
<java-pkg>.<world-segment>.<role>.{Imports, Exports}
world segment: lowerCamel of the world name
role segment:  host | guest  (literal)
```

- The **role segment is always present**, also when `--role host` or
  `--role guest` selects a single role. Rationale: switching
  `--role host` → `--role both` must never move any FQN.
- The **world always occupies its own segment** (both package styles): a WIT
  package may contain several worlds, whose `Imports` would collide otherwise.
- Interfaces are direction-independent and are generated **exactly once**,
  never duplicated per role. Under `--role both` the `host` and `guest`
  aggregate packages each reference the same interface types.

### 7.2 Aggregates

`Imports` and `Exports` are Java interfaces:

- Each imported (resp. exported) WIT interface gets one accessor method,
  lowerCamel of the interface name, returning the interface type:
  `IncomingHandler incomingHandler();`
- Inline world functions (`import foo: func(...)`) — and the functions of
  **inline world interfaces** (`import foo: interface { f: func(); }`) —
  become abstract methods on the aggregate directly, named lowerCamel, in
  world-item order. An inline interface gets no accessor (no named type
  exists for one to return).
- Inline world type definitions — including those declared inside inline
  world interfaces — land in the world package segment
  (`<java-pkg>.<world-segment>`), shared by both role packages. Resources
  inside inline interfaces are emitted there with their methods; the world
  package gets a `package-info.java` when it receives types (§9).
- Collisions between an accessor name and an inline function name go through
  the §4.3 mangle loop; an unresolvable collision is WJ0005.
- A world and an interface with the same name in one WIT package are rejected
  by upstream resolution before this spec applies. WJ0007 therefore covers
  package-level merges: two WIT packages (or versions) landing in one Java
  package via `--package-map` (§3.4) or a version-segment collision (§3.2)
  with same-named items.

### 7.3 Role Javadoc

- `--role host` (on `host.Imports`): *"Implemented by the host; called by the
  component."* (on `host.Exports`): *"Called by the host; implemented by the
  component."*
- `--role guest` reverses both phrasings (guest POV: imports are *called by
  the guest*, provided by the host; exports are *implemented by the guest*,
  called by the host). The aggregate names keep referring to WIT world
  imports/exports in every role — `guest.Imports` always holds the world's
  imports — only the Javadoc wording changes.
- `--role both` (default) generates both packages with host phrasing.

## 8. Support package

**There MUST be exactly one copy of each support type per JVM.** Support types
generated per-package would make `wasi.http.Result` and `wasi.io.Result`
incompatible types — cross-package signatures would not compile.

- Default FQN (**normative**): **`io.github.witjava.support`**.
  Overridable with `--support-package <fqn>`; overriding is runtime
  configuration, but the *default* is part of this spec and changing it is a
  breaking change (§15).
- Support content is versioned with the **mapping**, not the tool: an
  implementation of mapping v1 must emit byte-identical support sources for
  the same `--support-package` value regardless of its own version.
- Implementations MUST write the support sources next to the generated code
  (default), or skip them with `--no-support` (assuming the published
  `wit-java-support` artifact on the classpath).
- API surface is minimal and append-only: **no combinators**
  (`map`/`flatMap`/`orElse`/predicates) in v1. Methods may be appended in
  later vN; adding them in v1 freezes a larger contract forever.

### 8.1 Normative sources

Every file starts with this two-line license note, followed by a `package`
line parameterized by FQN (`{{PACKAGE}}` below); everything else is verbatim.
An implementation of mapping v1 MUST emit exactly these bytes for a given
`--support-package` value.

```java
// Copyright: the support package carries the mapping repository's license
// (Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT).

package {{PACKAGE}};
```

```java
// --- package-info.java ---
/**
 * Shared support types for WIT-generated Java declarations (mapping v1).
 *
 * <p>NaN note: WIT specifies canonical NaN; Java floating-point NaN
 * comparison semantics differ. Adapters lifting/lowering floats must not
 * rely on bit-exact NaN round-trips.
 */
@WitGenerated(mapping = "v1")
package {{PACKAGE}};
// (the annotation line precedes the package statement; outside the support
//  package the fully-qualified form is used, §9)

// --- Unit.java ---
/** Absent WIT type argument (empty tuple, one-sided result). */
public enum Unit { UNIT }

// --- Result.java ---
/** A WIT {@code result<T, E>}: either {@link Ok} or {@link Err}. */
public sealed interface Result<T, E> permits Result.Ok, Result.Err {

    /** Wrap a success value. */
    static <T, E> Result<T, E> ok(T value) {
        return new Ok<>(value);
    }

    /** Wrap an error value. */
    static <T, E> Result<T, E> err(E error) {
        return new Err<>(error);
    }

    /** The success case. */
    record Ok<T, E>(T value) implements Result<T, E> {}

    /** The error case. */
    record Err<T, E>(E error) implements Result<T, E> {}
}

// --- Nullable.java ---
/** Marks a nullable WIT {@code option<T>} under {@code --option-style=nullable}. */
@java.lang.annotation.Documented
@java.lang.annotation.Retention(java.lang.annotation.RetentionPolicy.RUNTIME)
@java.lang.annotation.Target(java.lang.annotation.ElementType.TYPE_USE)
public @interface Nullable {}

// --- WitGenerated.java ---
/** Marks WIT-generated packages and types. */
@java.lang.annotation.Documented
@java.lang.annotation.Retention(java.lang.annotation.RetentionPolicy.RUNTIME)
@java.lang.annotation.Target({java.lang.annotation.ElementType.PACKAGE,
        java.lang.annotation.ElementType.TYPE})
public @interface WitGenerated {
    /** Mapping version, e.g. {@code "v1"}. */
    String mapping();
}

// --- Tuple2.java .. Tuple8.java --- (same shape, arity-parameterized)
/** A WIT {@code tuple} with 2 components. */
public record Tuple2<A, B>(A v0, B v1) {}
```

Fields are `v0` … `v7` mirroring positional WIT tuple components.

## 9. Javadoc, annotations and file headers

- WIT doc comments → Javadoc, line structure preserved; blank lines inside a
  doc comment are dropped.
- HTML escaping: `<` → `&lt;`, `>` → `&gt;`, `&` → `&amp;`; a `@` at the
  start of a line → `&#64;` (otherwise it parses as a Javadoc tag); the
  sequence `*/` → `*&#47;` (otherwise it terminates the comment). Escaping
  applies to doc text, never to generated `{@code}`/`{@link}` markup the
  implementation itself emits.
- Generated Javadoc carries only content derived from the WIT (docs,
  `@param`/`@return`-worthy notes, the §5 notes). Implementations MUST NOT
  invent filler descriptions.
- Custom notes are written as prose sentences, **never** as `@` tags
  (doclint would fail): the §5.1 `char`/`u64` notes and the §5.11
  borrow/own notes.
- Every generated file starts (line 1) with:

```text
// @generated by wit-java <tool-ver>, mapping v1 — DO NOT EDIT
```

  `<tool-ver>` is the generating implementation's version. Byte-level tools
  (Tier 2) may pin their own version; Tier 1 ignores this line.
- **No license header** in generated files: generated output belongs to the
  user project; the only exception is the support package, whose sources
  carry the mapping repository's own license.
- Every generated package gets a `package-info.java` carrying
  `@WitGenerated(mapping = "v1")` plus the WIT package-level doc (nested
  style: an interface's own sub-package `package-info.java` also carries the
  interface doc). The support package's own `package-info.java` references
  the annotation by simple name; every other package MUST use the
  fully-qualified form `@<support-package>.WitGenerated(...)`, because
  `import` declarations cannot precede the package declaration in a
  `package-info.java`.
- `@WitGenerated` is RUNTIME-retention so downstream tools can detect
  generated code by reflection.

## 10. Diagnostics

- Every diagnostic MUST carry: its code (`WJnnnn`,
  [`error-codes.md`](error-codes.md)), a message, and the WIT source location
  (file, line, column) the condition originates from.
- Codes are frozen once published; new codes may only be appended.
- Implementations MUST report the code token `WJnnnn` on stderr in a
  machine-findable form; a message substring is NOT part of conformance
  (wording is free).
- Implementations SHOULD collect multiple diagnostics and report them
  together (collision errors otherwise surface one at a time).
- Exit codes: `0` success · `1` any diagnostic / usage error · `2` internal
  error.
- A run with diagnostics MUST NOT write output files (never emit Java that
  does not compile).

## 11. CLI contract

```text
wit-java generate <wit-path> --out <dir> [options]
wit-java check    <wit-path>            [options]
wit-java mapping-info --mapping-version v1
```

| Option | Default | Meaning |
|---|---|---|
| `--out <dir>` | — | output directory (`generate` only) |
| `--package-root <fqn>` | *(none)* | prefix for all mapped packages |
| `--package-map <file>` | *(none)* | TOML overrides (§3.4) |
| `--interface-package-style nested\|flat` | `nested` | §3.3 |
| `--mapping-version v1` | latest stable | must be a version the tool implements |
| `--support-package <fqn>` | `io.github.witjava.support` | §8 |
| `--no-support` | off | skip writing support sources |
| `--option-style optional\|nullable` | `optional` | §5.4 |
| `--u64 long\|BigInteger` | `long` | §5.1 |
| `--role host\|guest\|both` | `both` | §7 |
| `--features <name>...` | *(none)* | feature gates (§2), repeatable |
| `--all-features` | off | enable all features |
| `--world <name>` | *(all)* | restrict to named worlds, repeatable |

`check` runs the entire pipeline (resolve → map → IR → import resolve) but
writes nothing; it is the CI entry point. `mapping-info` prints the mapping
table from the same data the generator uses (never a second hand-written
table).

## 12. Determinism

Same input + same options → byte-identical output directory, on every host:

- File set, file order, import order, declaration order, member order:
  explicitly determined (files sorted by path; imports sorted
  lexicographically; declarations and members in WIT definition order).
- `\n` line endings, trailing newline on every file, UTF-8 without BOM.
- No timestamps, no locale-dependent formatting, no map/hash iteration order.
- Diagnostics, when collected, are ordered by (code, location) so error
  output is also deterministic.

## 13. Known limitations

Normative record of accepted semantic losses:
[`known-limitations.md`](known-limitations.md). An implementation MUST NOT
hide a listed loss silently; the Javadoc requirements in §5 exist for this.

## 14. Conformance

- Data: [`../conformance/`](../conformance/). Positive case = `case.wit` +
  `case.toml` (options) + `expected/` Java tree. Negative case = `case.wit` +
  `case.toml` + `expected-error.toml` (the expected `WJnnnn` code).
- **Pass (positive):** Tier 1 — canonical API digest of the generated tree
  equals the digest of `expected/`. Digest: parsed (not compiled) public API
  surface — packages, type names, kinds, supertypes, member signatures,
  modifiers — normalized and sorted; Javadoc prose, comments, whitespace and
  declaration order are excluded. The reference checker lives in
  `tools/checker` (JDK-only).
- **Pass (negative):** exit code non-zero, output names the expected code,
  and **no files are written**.
- Tier 2 (byte equality of an entire output tree, including Javadoc prose and
  ordering) is how the reference implementation tests its own determinism;
  a second implementation is never required to satisfy it.

## 15. Versioning and evolution

- Mapping **vN is append-only** after freeze: new WIT constructs unknown to
  vN MUST produce `unsupported in mapping vN` (WJ0001), never a silent new
  mapping. New mappings land in a new version.
- The support-package default FQN (§8) is part of the spec: changing it is a
  **breaking change** and requires a new mapping version.
- The reserved-word list (§4.2) and the error-code registry
  ([`error-codes.md`](error-codes.md)) are frozen once v1 freezes; both may
  only be extended, and extending them is breaking.
- Tool versions and mapping versions are orthogonal: one tool can implement
  several mapping versions; `--mapping-version` selects, defaulting to the
  latest **stable** (not merely latest) version.
- Frozen spec revisions are tagged `mapping/vN` in this repository.
